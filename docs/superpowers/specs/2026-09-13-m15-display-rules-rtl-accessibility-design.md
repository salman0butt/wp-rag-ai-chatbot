# M15 — Display Rules, Proactive Triggers, Multilingual/RTL & Accessibility Design

Status: AUTO-APPROVED FOR SCHEDULED AUTONOMOUS EXECUTION
Date: 2026-09-13
Milestone: M15

## 1. Context

M14 established one public widget mount authority (`PublicWidgetBootstrap`), one allow-listed public `WidgetConfig`, and one shared browser runtime (`src-js/widget-runtime.ts`) for floating, embedded, fullscreen, shortcode, and Gutenberg surfaces. M15 must add deterministic presence/engagement rules, proactive triggers, multilingual/RTL behavior, and accessibility hardening without creating a second widget or chat path.

The milestone is presentation policy only. Display-rule facts and browser state must never become authorization, retrieval, provider, model, embedding, vector-store, or conversation-ownership authority.

## 2. Goals

1. Let a bot define normalized, bounded display rules for URL/path, post type, authenticated/role audience, WooCommerce area, device class, schedule/day/time, first visit, and page-specific starters.
2. Add deterministic proactive triggers for delay, scroll threshold, exit intent, inactivity, and validated CSS-selector click targets.
3. Use one pure/testable rule evaluator with documented precedence and deterministic fixtures.
4. Reuse M14 public mount/runtime and appearance authorities.
5. Make locale/direction explicit, safe, and deterministic, including RTL layout semantics.
6. Respect keyboard navigation, screen readers, focus, reduced-motion preferences, and trigger cleanup.
7. Keep public/browser DTOs allow-listed and secret-free.

## 3. Non-goals

- No provider/model/embedding/vector-store selection changes.
- No alternate RAG/chat pipeline.
- No general marketing automation, campaigns, email/SMS, CRM workflows, or cross-site tracking.
- No arbitrary JavaScript, raw HTML, raw CSS, unbounded selectors, regex supplied directly to the browser, or request-level privilege assertions.
- No display rule may grant backend access or weaken capability/ownership checks.
- No commerce actions; those remain M18.

## 4. Architectural choice

### Recommended approach: normalized persisted rules + explicit runtime facts + one pure TypeScript evaluator

Persist one normalized allow-listed display configuration per bot, project it through the existing public widget configuration boundary, and evaluate it in the shared M14 browser runtime using explicit facts. Server-known facts are generated by WordPress while rendering the mount; browser-only facts are derived by a bounded browser adapter.

This is preferred over server-only evaluation because scroll, inactivity, exit-intent, viewport/device, and click-target signals are inherently browser events. It is preferred over split independent PHP/TypeScript rule engines because duplicated precedence/matching logic would drift. PHP validates/normalizes/persists and projects facts; TypeScript owns presentation evaluation only.

Client-side facts are **not security authority**. A visitor can always manipulate their own DOM/runtime; changing local visibility cannot grant backend privileges. All backend chat/access rules continue to enforce their existing server-side authority independently.

### Rejected alternatives

1. **A second M15 widget/runtime.** Rejected because it duplicates M14 surface and lifecycle authority.
2. **Duplicate rule evaluators in PHP and TypeScript.** Rejected because matching/precedence can diverge.
3. **Arbitrary callback/regex/JS rules.** Rejected for injection, performance, and auditability reasons.
4. **Sending raw WordPress user objects or role arrays to the browser.** Rejected. Project only bounded booleans/tokens needed by configured rules.

## 5. Data model

Create a normalized browser-safe `DisplayRulesConfig` with bounded collections and defaults. Exact persisted shape may evolve under TDD, but the authority must preserve these semantics:

```text
DisplayRulesConfig
  enabled: bool
  visibility:
    url_include: list<bounded URL/path pattern>
    url_exclude: list<bounded URL/path pattern>
    post_types: list<bounded slug>
    audience: all | authenticated | anonymous | selected_roles
    roles: list<bounded role slug>
    woo_areas: list<shop|product|cart|checkout|account>
    devices: list<desktop|tablet|mobile>
    schedule:
      timezone: site
      days: list<0..6>
      start: HH:MM | null
      end: HH:MM | null
  proactive:
    enabled: bool
    first_visit_only: bool
    delay_ms: bounded int | null
    scroll_percent: bounded int | null
    exit_intent: bool
    inactivity_ms: bounded int | null
    click_selector: validated bounded selector | null
  starters:
    default: bounded list<string>
    by_page: bounded list<{ pattern, prompts }>
  localization:
    locale: site | auto | supported explicit locale
    direction: auto | ltr | rtl
```

Rules are immutable values after normalization. Unknown keys fail closed at admin/persistence boundaries rather than being silently forwarded.

### Bounds

Implementation constants must be conservative and covered by tests. Initial design bounds:
- at most 32 include/exclude patterns combined;
- at most 16 roles/post types combined per category;
- at most 8 page-specific starter mappings;
- at most 4 prompts per starter set;
- each prompt <= 160 Unicode code points;
- delay/inactivity <= 10 minutes;
- scroll percent 1..100;
- selector <= 160 characters and restricted to ordinary id/class/attribute/tag selectors; no comma-separated selector lists or pseudo-elements;
- URL/path patterns use a small deterministic glob grammar, not arbitrary regex.

If existing repository conventions dictate tighter limits, use the tighter limits.

## 6. Runtime facts

One explicit `DisplayRuleFacts` value is evaluated. Facts are split by provenance but consumed by one pure evaluator.

### Server-projected facts

Generated only by `PublicWidgetBootstrap`/a dedicated server context resolver while rendering the public surface:
- normalized current path/URL components required for matching;
- current post type when available;
- `isAuthenticated` boolean;
- bounded role-match booleans/tokens needed for configured role rules, not a serialized WP user object;
- bounded WooCommerce area token when WooCommerce context exists;
- site timezone/locale/direction defaults.

These fields are not accepted from public REST chat requests and are not used for authorization.

### Browser-derived facts

Generated from browser state/events:
- viewport/device bucket;
- elapsed time since mount;
- scroll percentage;
- inactivity elapsed time;
- exit-intent occurrence;
- validated click-target occurrence;
- first-visit marker scoped to bot/site in browser storage;
- `prefers-reduced-motion`.

Browser observers only feed facts. They never invoke provider/RAG logic directly.

## 7. Deterministic evaluation and precedence

The evaluator returns a small decision object, not side effects:

```text
DisplayDecision
  visible: bool
  proactiveEligible: bool
  starters: list<string>
  locale: string
  direction: ltr|rtl
  reasons: bounded list<stable reason code>
```

Precedence is deterministic:

1. disabled configuration => hidden and no proactive trigger;
2. explicit URL exclusion => hidden;
3. any configured inclusion/audience/post/Woo/device/schedule gate that does not match => hidden;
4. otherwise widget surface is visible;
5. proactive eligibility is evaluated only after visibility is true;
6. first-visit gate applies before event triggers;
7. multiple configured proactive triggers are OR semantics: the first satisfied trigger may offer/open once for that mount/session;
8. manual user open always cancels pending proactive work for that mount;
9. page-specific starter match uses most-specific deterministic rule: exact path before bounded glob; first normalized rule wins among equal specificity;
10. explicit direction overrides locale-derived direction; otherwise RTL locales map to RTL and all others to LTR.

Exclude wins over include. A configured category is ANDed with other configured categories; values within the same category are ORed.

All reason codes and tie-breakers must be fixture-tested.

## 8. URL matching

Use a tiny deterministic matcher:
- exact path such as `/pricing`;
- prefix/suffix glob with `*` only, such as `/docs/*` or `*/checkout`;
- optional exact absolute same-origin URL normalized to path/query if existing requirements need it.

Do not compile arbitrary user regex. Normalize leading slash, length, wildcard count, and malformed values on persistence.

## 9. Trigger lifecycle

Create one trigger coordinator owned by each mounted widget runtime.

Responsibilities:
- register only observers/listeners required by normalized config;
- own at most one delay timer and one inactivity timer per mount;
- throttle scroll evaluation through existing browser scheduling primitives;
- use mouse exit intent only for pointer-capable desktop contexts;
- attach click targeting only to a validated selector and use delegated matching safely;
- cancel timers/listeners when the widget opens manually, proactively fires, becomes ineligible, or the mount is disposed;
- never trigger more than once per mount/session;
- never issue a chat request merely because a proactive UI prompt is shown.

Reduced motion disables nonessential animated transitions and any motion-dependent presentation; it does not silently change visibility rules.

## 10. First-visit semantics

First-visit is a local presentation hint, not identity tracking. Store only a small bot-scoped seen marker in local storage when available. If storage is unavailable, degrade safely to session-local behavior. No fingerprinting or cross-site identifier is introduced.

## 11. Page-specific starters

Starters are bounded plain text suggestions. They do not bypass chat submission, do not contain executable markup, and selecting one only populates/submits through the same M14 chat UI authority. Matching uses the same normalized URL matcher as visibility.

## 12. Multilingual and RTL

- Default locale derives from WordPress/site locale projected by the bootstrap.
- Runtime may use the document language as an `auto` fallback, but persisted config controls only supported normalized locale identifiers.
- Direction defaults from server/document direction, with explicit normalized override when configured.
- Apply `lang`/`dir` at the widget root/panel boundary, not globally to the host page.
- RTL mirrors directional layout concepts (message alignment, launcher side semantics where appropriate) without reversing logical content order, code, URLs, or source metadata.
- User-facing runtime labels introduced by M14 (`Chat`, `Close`, loading/error/retry/copy/source labels) must move behind one bounded message catalog/localization authority rather than being independently hard-coded in new M15 components.
- Unsupported locale values fall back to site/default messages and direction.

Initial milestone scope should establish the localization architecture and at least English plus one RTL fixture/locale path; it should not claim a complete translation catalog for every locale.

## 13. Accessibility

M15 extends, not replaces, M14 semantics:
- native buttons/inputs remain preferred;
- focus moves/restores according to existing floating dialog behavior;
- proactive prompts must not steal focus automatically;
- screen-reader status announcements are concise and non-repetitive;
- keyboard users can dismiss/open/operate all proactive UI;
- Escape behavior remains deterministic;
- RTL does not break tab order or DOM reading order;
- reduced-motion preference removes nonessential animation;
- color/appearance changes continue through normalized M14 appearance authority.

## 14. Persistence and admin boundaries

Follow the M14 appearance pattern:
- immutable normalized PHP config value;
- bot-scoped repository persistence;
- capability-protected administrator REST read/write contract;
- public `WidgetConfig` projection contains only normalized display/localization data;
- no arbitrary request-level runtime override on public widget/chat REST routes.

Admin UX edits persisted config through the existing admin app and previews through the same pure evaluator/runtime projection used publicly. Preview-specific simulated facts are local admin-only inputs and are never persisted as authoritative user/session facts.

## 15. Security and privacy

- Display rules are UX only; never reuse them as capability checks.
- No WP user object, email, user ID, capability map, provider secret, model name, embedding/vector configuration, or raw request headers enter public config.
- Role targeting should expose only the minimal normalized match data needed by presentation logic.
- Selector/path/prompt inputs are bounded and normalized.
- No raw HTML/CSS/JS execution channel.
- First-visit storage is bot-scoped and contains no personal data.
- Proactive prompts do not auto-send chat messages.

## 16. Performance

- Pure rule evaluation is O(number of bounded rules).
- No polling loop; event/timer driven only.
- At most one listener per event type per mount, with deterministic teardown.
- Reuse existing conditional asset loading.
- Do not add network requests solely to evaluate display rules.
- Keep config/facts payload small and bounded.

## 17. Failure behavior

- Invalid persisted/admin input is rejected at the protected boundary.
- Missing optional config normalizes to conservative defaults: widget behavior remains equivalent to M14 (visible, no proactive trigger).
- Missing browser APIs disable only the dependent proactive signal.
- Malformed public configuration fails closed for proactive behavior and does not crash the widget runtime.
- Localization failure falls back to default messages/direction.
